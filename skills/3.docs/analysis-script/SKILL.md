用于系统性地解析数据脚本项目（Python ETL、定时任务、数据管道等），输出标准化文档。

## 我的要求
- 如果是一组脚本（如 `solidify_*.py` 系列），先输出一张**脚本总览表**，再对每个脚本分别输出完整七维分析。
- 严格按照skill的要求去生成报告, 不要生成多余维度的分析


## 输入收集
在开始分析前，先判断用户提供了哪些材料，缺少的主动索取：

| 材料 | 用途 | 是否必须 |
|------|------|---------|
| 脚本代码文件 / 粘贴内容 | 分析入口、逻辑、SQL、依赖 | ✅ 必须 |
| 执行日志 | 计算运行时长、各阶段耗时 | ✅ 运行时长维度必须 |
| 调度配置（cron / 任务平台截图） | 确认启动时间和触发方式 | 🔶 没有则标注"未知，请补充" |
| 项目目录结构 | 识别入口文件和模块关系 | 🔶 没有则从代码推断 |

> 如果用户没有提供执行日志，在"运行时长"一栏注明：`⚠️ 需要用户提供执行日志，当前无法统计`

## 输出格式

输出一份完整的 Markdown 分析报告，结构如下：

---

### 一、脚本概览

用 1~3 句话概述这组脚本的整体业务目标和技术方案。

---

### 二、入口文件与职责

| 文件 | 职责描述 | 取数范围 | 核心逻辑摘要 |
|------|---------|---------|------------|
| `main.py` | 整体调度入口，串联各子任务 | - | 依次调用 A→B→C 模块 |
| `solidify_daily.py` | 写入每日汇总数据到 ClickHouse | T-1 日 | 按日期分区替换 |
| `fetch_orders.py` | 从 TikTok Shop API 拉取订单 | 近 7 天 | 游标分页，写入 MySQL 临时表 |

> 规则：必须是脚本启动的入口文件, 每个文件单独一行；职责聚焦业务语义，不要写"读取文件"这种技术废话；核心逻辑摘要控制在 20 字以内。

---

### 三、调度与运行时长

| 脚本 | 启动方式 | 启动时间 | 平均运行时长 | 取数范围 | 各阶段耗时 |
|------|---------|---------|------------|---------|----------|
| `solidify_daily.py` | cron 定时 | 每天 02:00 | ~15 min | 前一天全天 | 拉取数据 3min / 写 CH 12min |
| `fetch_orders.py` | 手动触发 | 按需 | ⚠️ 需执行日志 | ⚠️ 需明确 | - |

**运行时长分析来源**：从用户提供的执行日志中提取 `start_time` / `end_time`，或日志中的耗时打印。

若日志包含类似格式，提取关键时间点：
```
[2024-01-15 02:00:01] START solidify_daily
[2024-01-15 02:14:37] END solidify_daily  total: 873s
```

---

### 四、数据范围

#### 读取（Source）

| 数据源 | 表/接口 | 时间范围 | 备注 |
|--------|---------|---------|------|
| MySQL `kol_db` | `orders`, `creators` | 近 7 天 | 按 `created_at` 过滤 |
| ClickHouse `tiktok_media` | `daily_stats` | 按日期分区 | 读取 T-1 数据 |
| TikTok Shop API | orders endpoint | 动态时间窗口 | 游标分页 |

#### 写入（Target）

| 目标库 | 表 | 写入方式 | 说明 |
|-------|----|---------|------|
| ClickHouse `asia` | `creator_daily` | 分区替换（REPLACE PARTITION） | 幂等写入 |
| MySQL `kol_db` | `tmp_order_sync` | TRUNCATE + INSERT | 临时中间表 |

---

### 五、前后依赖

| 脚本 | 上游依赖 | 下游依赖 | 约束说明 |
|------|---------|---------|---------|
| `fetch_orders.py` | TikTok Shop API 授权 Token 有效 | `solidify_product.py` 读取 `tmp_order_sync` 表 | 需在 API Token 过期前完成 |
| `solidify_daily.py` | `fetch_orders.py` 写入 `tmp_order_sync` 表 | `report_generator.py` 读取 ClickHouse `creator_daily` 表<br>`dashboard_refresh.sh` 触发缓存刷新 | 必须在 X 完成后 N 分钟内启动，否则数据窗口错位 |

**整体执行时序**

```
00:15 fetch_orders.py ━━━┓
                          ┃ 写入 MySQL tmp_order_sync
                          ┗━━━→ 
                                ↓
02:00 solidify_daily.py ━━━━━━┫ 固化到 ClickHouse creator_daily
                                ↓
                          ClickHouse 数据就绪
                                ↓
03:00 report_generator.py ━━━━┫ 生成报表
                                ↓
03:30 dashboard_refresh.sh ━━━┫ 刷新缓存
                                ↓
                          前端/BI 完整数据可用
```

**关键约束**

- `fetch_orders.py` 与下游竞态：00:15 写入数据，假设 `solidify_daily.py` 在 02:00 启动，时间窗口需确保数据完整性
- `solidify_daily.py` 数据完整性风险：依赖上游已将数据完整写入 MySQL，无前置检查
- `report_generator.py` 必须在固化完成后执行：需要从 ClickHouse 读取固化后的数据

### 六、问题 / 风险 / 优化点

**fetch_orders.py**

| 类型 | 位置 | 描述 | 严重程度 |
|------|------|------|---------|
| ⚠️ 风险 | 整体 | API Token 过期无重试，静默失败导致数据缺失 | 🔴 高 |
| ⚠️ 风险 | 写入逻辑 | 无幂等校验，重复执行会重复写入 | 🟡 中 |
| 💡 建议 | 日志 | 缺少结构化日志，排查困难，建议加 elapsed_time 打点 | 🟢 低 |

**solidify_daily.py**

| 类型 | 位置 | 描述 | 严重程度 |
|------|------|------|---------|
| 🐛 Bug | `L45` | NaN 未处理，写入 ClickHouse 时报 type error | 🔴 高 |
| 🚀 优化 | `L80-120` | 循环逐行 INSERT，改 executemany 或批量写入性能提升 10x | 🟡 中 |
| 🚀 优化 | ClickHouse 查询 | 使用 OFFSET 分页，数据量大时内存溢出，改游标分页 | 🟡 中 |

> **严重程度说明**：🔴 高（会导致数据错误/脚本失败） / 🟡 中（影响性能或稳定性） / 🟢 低（体验优化）

### 七、跑数要点

**fetch_orders.py**

- **幂等性**：⚠️ 直接 INSERT 不幂等，重跑会重复写入
- **时间参数**：默认昨天，支持 `--date` 参数
- **重跑/补跑策略**：支持 `--start_date` / `--end_date` 补跑，需先清空目标表
- **关键参数**：
  - `--date`: 昨天
  - `--batch_size`: 1000
- **异常处理**：中断后部分数据已写入，无事务保护；⚠️ 无告警

**solidify_daily.py**

- **幂等性**：✅ REPLACE PARTITION 天然幂等
- **时间参数**：默认 T-1，支持 `--date` 参数
- **重跑/补跑策略**：可直接重跑任意历史日期，无需暂停下游
- **关键参数**：
  - `--date`: 昨天
  - `--dry_run`: False
- **异常处理**：中断后数据回滚，分区级事务；钉钉告警

> **规则说明**：每个脚本单独列出；幂等性需明确写入方式（REPLACE PARTITION / TRUNCATE+INSERT / 直接 INSERT）；时间参数说明默认值和如何指定；关键参数只列最重要的 2-3 个；异常处理说明中断后状态和告警方式。输出格式可采用表格或列表。

## 分析原则

1. **代码优先**：所有结论必须有代码依据，不要凭空推断。
2. **日志驱动时长**：运行时长必须来自真实日志，没有日志则明确标注"⚠️ 需执行日志"。
3. **SQL 要扫表名**：数据范围部分必须扫描代码中所有 SQL 语句，提取 `FROM`、`JOIN`、`INSERT INTO`、`REPLACE PARTITION` 涉及的表。
4. **风险要具体**：问题描述要精确到文件名+行号（如能定位），不写"可能有性能问题"这种泛泛而谈。
5. **跑数要点要实用**：站在"我要今天手动跑一次这个脚本"的视角写，确保接手人能直接操作。

## 特殊情况处理

### 只有部分材料
- 没有日志：运行时长栏注明 `⚠️ 需执行日志`，其余维度正常分析。
- 没有调度配置：启动时间标注 `⚠️ 未知`，从代码注释 / README 中尝试推断。
- 只有代码无上下文：完成能分析的维度，对依赖关系标注 `⚠️ 需确认`。

### ClickHouse 相关脚本（kol_outreach 项目常见）
重点关注：
- `REPLACE PARTITION` / `INSERT INTO` 写入方式（影响幂等性）
- `ReplicatedMergeTree` ZooKeeper 路径（多实例风险）
- OFFSET vs 游标分页（内存溢出风险）
- session_id / 连接管理（长时间运行的连接复用问题）
