### 一、脚本基础信息

针对每个脚本,整理成一张表:

| 脚本 | 功能/职责 | 启动时间 | 取数范围 | 耗时 | 前置依赖(读取) | 后置依赖(写入) |
|------|----------|---------|---------|------|--------------|--------------|
| `fetch_orders.py` | 从 TikTok Shop API 拉取订单 | 每天 00:15 | 近 7 天订单 | ~5 min | TikTok Shop API | MySQL `tmp_order_sync` 表 |
| `solidify_daily.py` | 固化每日汇总数据到 ClickHouse | 每天 02:00 | T-1 日全天 | ~15 min | MySQL `tmp_order_sync`<br>ClickHouse `daily_stats` | ClickHouse `creator_daily` 分区 |

**字段说明**:
- **功能/职责**: 用 1 句话说清楚这个脚本做什么(业务语义,不要写"读取文件"这种技术废话)
- **启动时间**: cron 时间 / 手动触发 / 按需,如无调度配置则标注 `⚠️ 未知`
- **取数范围**: 时间窗口(如"T-1 日"、"近 7 天"、"动态参数"),无法从代码确定则标注 `⚠️ 需确认`
- **耗时**: 从执行日志提取,没有日志则标注 `⚠️ 需执行日志`
- **前置依赖(读取)**: 脚本需要从哪些表/接口读数据(格式:`库名.表名` 或 `API 名称`)
- **后置依赖(写入)**: 脚本处理后的数据存入哪些表(格式:`库名.表名`,注明写入方式如"分区替换"、"TRUNCATE+INSERT")

> 如果没有日志,耗时栏写 `⚠️ 需执行日志`;如果没有调度配置,启动时间写 `⚠️ 未知`

### 三、问题/风险/优化点

针对每个脚本,列出发现的问题:

**fetch_orders.py**

| 类型 | 位置 | 描述 | 严重程度 |
|------|------|------|---------|
| ⚠️ 风险 | 整体 | API Token 过期无重试,静默失败导致数据缺失 | 🔴 高 |
| ⚠️ 风险 | 写入逻辑 | 无幂等校验,重复执行会重复写入 | 🟡 中 |
| 💡 建议 | 日志 | 缺少结构化日志,排查困难 | 🟢 低 |

**solidify_daily.py**

| 类型 | 位置 | 描述 | 严重程度 |
|------|------|------|---------|
| 🐛 Bug | `L45` | NaN 未处理,写入 ClickHouse 时报 type error | 🔴 高 |
| 🚀 优化 | `L80-120` | 循环逐行 INSERT,改批量写入性能提升 10x | 🟡 中 |

> **严重程度**: 🔴 高(导致数据错误/脚本失败) / 🟡 中(影响性能或稳定性) / 🟢 低(体验优化)

### 四、脚本执行要点

针对每个脚本,整理手动执行时的关键信息:

**fetch_orders.py**

- **幂等性**: ⚠️ 直接 INSERT 不幂等,重跑会重复写入
- **时间参数**: 默认昨天,支持 `--date YYYY-MM-DD`
- **重跑/补跑策略**: 支持 `--start_date` / `--end_date` 补跑,需先手动清空目标表
- **关键参数**: `--date`(默认昨天) / `--batch_size`(默认 1000)
- **异常处理**: 中断后部分数据已写入,无事务保护;⚠️ 无告警

**solidify_daily.py**

- **幂等性**: ✅ REPLACE PARTITION 天然幂等
- **时间参数**: 默认 T-1,支持 `--date YYYY-MM-DD`
- **重跑/补跑策略**: 可直接重跑任意历史日期,无需暂停下游
- **关键参数**: `--date`(默认昨天) / `--dry_run`(默认 False)
- **异常处理**: 中断后数据回滚,分区级事务;钉钉告警

## 分析原则

1. **代码优先**: 所有结论必须有代码依据,不要凭空推断
2. **日志驱动耗时**: 耗时必须来自真实日志,没有日志则标注 `⚠️ 需执行日志`
3. **SQL 要扫表名**: 必须扫描代码中所有 SQL 语句,提取 `FROM`/`JOIN`/`INSERT INTO`/`REPLACE PARTITION` 涉及的表
4. **风险要具体**: 问题描述要精确到文件名+行号(如能定位),不写"可能有性能问题"这种泛泛而谈
5. **执行要点要实用**: 站在"我要今天手动跑一次这个脚本"的视角写,确保接手人能直接操作

---

## 特殊情况处理

- **没有日志**: 耗时栏注明 `⚠️ 需执行日志`,其余维度正常分析
- **没有调度配置**: 启动时间标注 `⚠️ 未知`,从代码注释/README 推断
- **只有代码无上下文**: 完成能分析的维度,依赖关系标注 `⚠️ 需确认`

### ClickHouse 相关脚本重点关注

- `REPLACE PARTITION` / `INSERT INTO` 写入方式(影响幂等性)
- OFFSET vs 游标分页(内存溢出风险)
- session_id / 连接管理(长时间运行的连接复用问题)
